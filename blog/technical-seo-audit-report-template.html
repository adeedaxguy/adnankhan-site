1. Scope and baseline

Start with the environment and the exact surface being reviewed. This prevents a developer from fixing a symptom on one URL while the same template-level defect remains elsewhere.

3. Crawl, indexation, and canonical checks

  • Confirm important URLs return the intended status, render useful content, and are not blocked by robots or a noindex directive.
  • Compare canonical tags, redirects, sitemap URLs, internal links, and the preferred final URL.
  • Separate intentional redirects and alternates from accidental duplication or conflicting canonical signals.
  • Review discovered-but-not-indexed URLs for thinness, duplication, weak internal links, or low business value before requesting indexing.

4. Rendering, performance, and mobile checks

AreaEvidenceAcceptance example

Core Web VitalsField data when available; lab data for diagnosisRelease does not regress the chosen performance budget.
Images and fontsTransfer size, dimensions, loading behaviorNo oversized hero asset, layout shift, or invisible first-screen text.
Mobile pathViewport screenshots and interaction testNavigation, CTA, form, and validation work without overlap or horizontal scroll.

5. Structured data and answer clarity

Validate syntax, then validate truth. Schema should identify the visible page type, organization, service, article, breadcrumb, or FAQ content without inventing reviews, ratings, locations, pricing, or claims. The first relevant section should also state the answer in plain language so searchers and answer systems do not have to infer it.

6. Release and validation log

  1. Record the commit, deployment, changed templates, and rollback path.
  2. Retest the exact reproduction steps and every affected URL pattern.
  3. Verify title, description, canonical, robots, schema, sitemap membership, internal links, and the lead action.
  4. Check representative desktop and mobile views.
  5. Set a measurement date for GSC visibility, landing-page behavior, and key events; do not promise an immediate ranking change.

FAQ

What makes a technical SEO finding actionable?

An actionable finding names the affected URL or pattern, shows reproducible evidence, explains the impact, assigns an owner, defines acceptance criteria, and records a validation method.

Should every technical SEO warning be fixed?

No. Classify findings as fix, expected/no action, or monitor. Prioritize access, indexation, canonical, rendering, performance, and structured-data issues that affect important pages.
